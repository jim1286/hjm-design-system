# AuthProviderButton contract

**문제.** 제공자 브랜드 규정을 따르는 소셜 로그인 버튼. BurnTok이
`.hjm-button.bt-provider-google` 네 줄로 HJM 버튼을 덮어 쓰던 자리다.

**왜 Button의 tone이 아닌가.** HJM의 tone은 **의미**다 — primary/secondary/danger는
팔레트를 따라 테마와 함께 움직인다. 제공자 버튼의 색은 의미가 아니라 **남의 브랜드
자산**이고, 각 제공자가 배경·글자·테두리를 가이드라인으로 규정한 뒤 심사에서 그대로
쓰기를 요구한다. tone을 하나 더 만들면 HJM 팔레트가 그 색을 다시 칠할 수 있게 되고,
그 순간 계약이 거짓말이 된다. 그래서 별도 컴포넌트로 두고, 값의 출처가 HJM이 아니라는
사실을 타입과 주석으로 드러낸다.

**소유 경계.**

| | 소유자 | 내용 |
| --- | --- | --- |
| 색·로고 모양 | 제공자 | `authProviderPalettes`가 가이드라인 값을 그대로 옮긴다 |
| 로고 자산 | 제품 | 재배포 조건이 제공자마다 달라 HJM이 번들하지 않는다. `logo` 슬롯으로 받는다 |
| 문구 | 제품 | 요구 표현이 제공자·언어마다 다르다. renderer가 만들지 않는다 |
| 높이·radius·타깃·포커스·배치 | HJM | 네 개가 세로로 쌓이는 화면에서 줄이 맞아야 한다 |

**테마의 역할은 선택뿐이다.** `resolveAuthProviderSurface(provider, theme)`는 제공자가
스스로 규정한 light/dark 변형 중 하나를 고를 뿐 색을 만들지 않는다. Google과 Apple은
어두운 변형을 따로 규정하고, Kakao·Naver는 브랜드색 자체가 정체성이라 다크에서도 같다.

**포커스 링은 바깥에 그린다.** `#FEE500`부터 `#000000`까지 어떤 배경 위에서도 보여야
하므로 `focusOutlineOffset`으로 fill 밖에 둔다.

**로그인 화면의 진행 상태는 카드가 소유한다.** 2026-10-01 사용자 요청으로 로그인 조합은
`AuthScreenLayout`의 pendingLabel을 사용한다. 모든 제공자 버튼을 숨기고 기존 카드 크기에서
중앙 로딩 하나만 보여 준다([로그인 화면 계약](auth-screen.md)). 버튼 label은 제품이 제공자
이름만 전달한다. 이전 버전 소비와 단독 버튼의 호환성을 위해 descriptor.busy는 유지하며,
카드 진행 상태와 동시에 사용하지 않는다.
단독 버튼이 busy이면 로고와 글자는 자리를 유지한 채 시각적으로 숨기고 카드 중앙에
스피너 하나만 보인다. 버튼의 접근성 이름과 높이·폭은 유지한다. 2026-10-02 사용자 요청으로
기존의 글자 옆 스피너 표현을 제거했다. 소셜 버튼마다 글자와 스피너를 나란히 두는 대안은
로딩 중 시선이 분산되고 버튼 폭도 달라져 채택하지 않았다.

**값의 출처.** 각 제공자의 공개 브랜드 가이드라인(2026-09 확인). 가이드라인이 바뀌면
`authProviderPalettes` 한 곳만 고친다.
