# ContextMenu contract

**문제.** 포인터 위치에서 열리는 메뉴 — 우클릭, 그리고 터치의 길게 누르기.

**Menu와 목록은 같고 앵커가 다르다.** Menu는 트리거 버튼에 붙고 ContextMenu는 이벤트가
일어난 **좌표**에 붙는다. 항목 타입은 `MenuItemDescriptor` 그대로다. 두 번째 항목 어휘를
만들면 tone·shortcut·disabled 규칙이 두 곳에서 갈라진다.

**트리거가 없다는 점이 접근성까지 번진다.** 버튼이 없으므로 키보드 사용자에게 여는 방법을
따로 줘야 한다(Shift+F10, 또는 메뉴 키). 그것을 빼면 마우스 없이는 존재하지 않는 기능이
된다 — 이 계약이 여는 이유(`openReason`)를 값으로 갖는 이유다.

**키보드로 열 때의 앵커는 초점 요소의 상자다.** 좌표가 없다고 (0,0)에 띄우면 메뉴가 방금
초점이 있던 항목과 무관해 보인다. `resolveContextMenuAnchor`가 이 판단을 갖고 있고,
좌표도 초점 상자도 없으면 렌더링 대신 던진다. 실제 메뉴가 포털에 마운트된 뒤 메뉴에 초점을
옮기고 `aria-activedescendant`로 활성 항목을 알린다. 열기 직전의 초점 요소는 보관한다.

**Escape 또는 항목 실행으로 닫으면 열었던 요소에 초점을 돌린다.** 바깥을 눌러 닫을 때는
사용자가 누른 바깥 요소의 초점을 유지한다. 좌표에서 열렸다고 초점까지 떠 있으면 다음 Tab이
문서 처음으로 간다.

**화면 가장자리와 긴 항목도 다룬다.** 메뉴가 포털에 표시된 다음 실제 크기로 위치를 화면 안에
맞춘다. 긴 한글·공백 없는 항목명은 줄바꿈해 전체 명령을 읽을 수 있게 한다. 임의의 고정 크기
추정은 글꼴과 줄바꿈에 따라 메뉴가 다시 화면 밖으로 나갈 수 있어 사용하지 않는다.

**브라우저 기본 메뉴를 제품이 소유한 표면에서만 대체한다.** 텍스트 선택·링크·이미지 위의
기본 메뉴를 빼앗으면 복사·새 탭 열기를 사용자에게서 뺏는 것이다.

**Web 전용.** 네이티브의 길게 누르기 메뉴는 OS가 제공하는 표면이라 같은 계약이 아니다.

React 구현은 `packages/react/test/context-menu.interactions.browser.test.tsx`에서 Chromium으로
포인터 좌표 열기, 키보드 열기, 활성 항목 안내, Escape·실행 후 초점 복귀, 작은 화면에서의 긴
항목 배치를 검증한다.
