# 화면과 구성 선택

검토일: 2026-10-13

2026-10-13 설계 점검에서 화면 이름만으로 공통 화면을 강제하면 저장·스크롤·권한 흐름이
다른 제품까지 같은 틀에 맞출 수 있음을 확인했다. 화면 → 구성 → 컴포넌트 → 토큰 순으로
찾되, 아래 행동과 소유권이 맞는지 먼저 판단한다.

## 선택 기준

| 선택 | 조건 | 구현 경로 |
| --- | --- | --- |
| 그대로 사용 | 영역 순서, 저장 시점, 상태 교체, 스크롤 소유가 제품과 맞는다 | 공통 화면에 데이터·문구·콜백을 연결 |
| 공개 슬롯으로 확장 | 공통 행동은 같고 헤더·본문 콘텐츠·보조 행동만 다르다 | header·notice·footer 등 해당 API의 공개 슬롯 사용 |
| 제품 전용 구성 | 저장·탐색·권한 흐름 또는 가상화·스크롤 구조가 공개 API로 표현되지 않는다 | 기존 HJM 구성·컴포넌트로 제품에서 조합하고 차이를 기존 코드/작업 기록에 설명 |

공개 슬롯으로 해결할 수 있는 틀·상태 엔진은 복제하지 않는다. 제품 전용 구성도 semantic token,
접근성·입력·실패 복구 계약을 유지한다. 내부 selector나 제거된 style prop은 확장 경로가 아니다.
여러 제품이 공유하는 공백이면 공통 API의 의미 있는 축으로 검토한다. 별도 승인·ADR은 자동 요구하지 않는다.

## 선택 전에 확인할 것

- **저장:** 즉시 저장인지 일괄 저장인지, pending의 소유자와 실패 시 마지막 확인값·초안이 어떻게 남는지.
- **스크롤:** host와 본문 중 누가 스크롤하는지, 목록 가상화·페이지 추가·위치 복구가 필요한지.
- **상태:** 최초 조회의 본문 교체와 저장/재조회 오류의 비차단 notice가 구분되는지.
- **권한:** 접근 제한에서 작성·전송을 숨길지, 읽기와 쓰기 권한이 다른지.
- **플랫폼:** Web 포커스와 Native 키보드·safe area를 누가 처리하는지. 같은 inset·스크롤을 중복 적용하지 않는다.

SettingsScreen의 행별 즉시 저장은 행 콜백에 제품 mutation을 연결한다. 일괄 저장도 공개 footer와
notice로 표현되면 같은 API를 사용한다. CommentThreadScreen의 데이터 구조나 스크롤이 대규모
가상화에 맞지 않으면 이름만 보고 강제하지 않고 ScreenLayout과 적합한 목록을 조합한다.

## 상태와 버전 읽기

| 정보 | 원본 | 해석 |
| --- | --- | --- |
| 제공 기준 | 컴포넌트 지침의 적용 버전과 설치 패키지 exports/타입 | 확인한 기본 API의 게시 버전이며 최초 출시 버전이나 후속 prop 전체의 제공 보증은 아님 |
| 플랫폼 지원·API 안정성 | 설치 버전 catalog의 surfaceStatus와 선택형 API 계약 | canonical과 supplemental·optional API를 구분. catalog 밖 API를 자동 stable로 간주하지 않음 |
| Storybook 분류 | 스토리 제목의 배포/실험 | 예제 분류. npm 게시·소비 앱 반영을 의미하지 않음 |
| 검증 | 해당 SHA·플랫폼·환경의 실행 결과 | 타입·브라우저·host mock·기기 결과의 범위를 구분 |

구성·화면은 여러 API를 사용하므로 별도 라이브러리 버전을 복제하지 않고 각 API 지침을 참조한다.
설치 버전보다 새 문서의 prop은 설치된 타입과 export에서 다시 확인한다.
