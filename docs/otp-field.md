# OtpField contract

## 문제

문자로 온 인증번호를 한 자씩 여러 칸에 입력한다. Ant Design `Input.OTP`와 `direct`
crosswalk를 따른다(`Input`의 decomposed target 중 하나).

## 접근성이 본체다: 여러 칸이지만 하나의 값이다

**판정.** OtpField는 **하나의 포커스 가능한, 하나의 접근 가능한 이름·값을 가진 텍스트
컨트롤**이다 — 칸마다 별도로 포커스를 받는 N개의 실제 input이 아니다. 화면에 보이는
N개의 칸은 그 하나의 컨트롤이 가진 문자들을 보여주는 **장식**일 뿐이다
(`getOtpFieldSlotValues`).

**근거.** 칸마다 독립된 실제 input을 만들면 스크린 리더는 각 칸에 포커스가 갈 때마다
"6개 중 3번째, 빈 칸" 같은 것을 읽는다 — 사용자는 자신이 지금 무엇을 입력하고 있는지
(인증번호 전체 중 어디까지 왔는지, 지금까지 뭘 입력했는지) 알 수 없다. 이건 이 종류의
컴포넌트가 접근성에서 가장 흔히 실패하는 지점이다. 반면 하나의 실제 텍스트 필드에
글자 간격(letter-spacing) 스타일과 그 위에 겹쳐 그리는 장식 칸 테두리를 쓰면, 화면
읽기는 평범한 한 텍스트 필드("인증번호, 123 입력됨" 같은 하나의 이름과 값)이고, 보기에는
여전히 칸이 나뉜 것처럼 보인다. 시각적 유연성(칸별 강조색 등)도 잃지 않는다 —
`getOtpFieldSlotValues`가 칸별 문자를 그대로 주므로 장식 칸 하나하나를 다르게 칠하는
것은 여전히 가능하다.

## 붙여넣기·입력·지우기가 거의 공짜인 이유

실제 input이 하나이므로 타이핑·붙여넣기(중간 선택 영역에 붙여넣기 포함)·Backspace는
**모두 플랫폼의 기본 텍스트 편집**이 처리한다 — 문자 삽입 위치, 선택 영역 교체, 커서
이동을 이 패키지가 다시 구현하지 않는다. 브리프가 요구한 "지우기 동작"(빈 칸에서
Backspace → 앞 칸으로)도 이 모델에서는 별도 로직이 필요 없다 — 마지막 문자 바로 뒤
커서에서 Backspace를 누르면 원래 텍스트 필드가 마지막 문자를 지우고 커서를 한 칸
앞으로 옮기는 것과 정확히 같은 동작이기 때문이다.

그래서 HJM이 실제로 소유하는 판단은 딱 하나 — **편집 결과로 나온 원시 문자열을 어떻게
정리하는가**(`resolveOtpFieldValue(length, rawText)`): 숫자만 남기고, `length`를 넘지
않게 자른다. 타이핑이든, 붙여넣기든, 중간 위치에 붙여넣은 결과든 항상 이 하나의
함수로 들어온다 — 그래서 이 계약이 함수를 여러 개(칸별 입력, 칸별 붙여넣기, 칸별
지우기) 만들지 않고 하나만 갖는다.

**경계 입력(테스트로 잠갔다).**

- 길이 초과: `"1234567890"` → `length`만큼 자른다(던지지 않는다).
- 숫자가 아닌 문자: `"12-34 56"`, `"abc123def456"` → 숫자만 남긴다(거부하지 않는다,
  붙여넣은 문자열에 공백·하이픈이 섞여 오는 실제 SMS 문구를 그대로 허용하기 위해서다).
- 중간 위치에 붙여넣기: 실제 input에서는 "칸 3에 붙여넣기"가 아니라 "이미 있던
  텍스트의 중간에 붙여넣어 병합된 새 문자열"로 이 함수에 도착한다 — 그 이미
  병합된 문자열을 정리하는 것으로 충분하다(테스트: `"12" + "99"(붙여넣음) + "34"` →
  `"129934"`, `length=4`면 `"1299"`로 자름).

`value.length > length`인 **커밋된 descriptor**는 여전히 던진다
(`validateOtpFieldDescriptor`) — 이건 편집 경로가 아니라 "이미 잘못된 상태를 그대로
렌더링하려는" 렌더러 버그 신호다. 편집 중(자름)과 커밋된 상태 검증(던짐)은 다른
문제다.

## 값은 항상 빈틈없다

`OtpFieldDescriptor.value`는 항상 인덱스 0부터 채워진 문자열이다 — 칸 2는 채워지고 칸
0~1은 비어 있는 상태를 표현하지 않는다(`getOtpFieldSlotValues`가 인덱스 `i`는
`i < value.length`일 때만 채워졌다고 보는 것과 정확히 같다). 이 하나의 불변식 때문에
타이핑·붙여넣기·지우기가 모두 "평범한 문자열 편집"으로 환원된다 — 빈틈을 허용했다면
칸별 위치 계산을 이 패키지가 다시 만들어야 했을 것이다.

## 숫자만 받는다

인증번호는 이 브리프가 설명하는 그대로 숫자다. 영숫자 혼합 OTP는 지금 계약에 없다 —
문자 집합을 설정 가능하게 만들면 검증되지 않은 패턴을 미리 얹는 것이 된다. 실제
필요가 나오면 그때 `characterPattern` 같은 축을 연다.

## HJM 기본값

- 칸(`slot`) 테두리는 새 팔레트를 만들지 않고 `fieldFrameContract`의 `border`/
  `focusBorder`/`invalidBorder`/`radius`/`borderWidth`를 그대로 쓴다 — 칸 하나하나가
  작은 Field 프레임이라는 뜻이다. 채워진 칸의 테두리만 `content.brand`로 강조한다.
- `support`(hint/error)는 `formSupportContract`를 그대로 쓴다.

## 플랫폼 번역

- Web: 실제 `<input>` 하나(`type="text"`, `inputMode="numeric"`, `maxLength={length}`,
  `autoComplete="one-time-code"`). 화면에는 letter-spacing과 겹쳐진 칸 테두리로
  나뉜 것처럼 보이지만 접근 가능한 이름과 값은 하나다. 클릭으로 특정 칸 근처를
  누르면 그 위치 근처로 네이티브 캐럿이 이동한다 — 별도 포커스 이동 로직이 필요
  없다.
- Native: `TextInput` 하나, `keyboardType="number-pad"`, `maxLength={length}`. 칸은
  같은 방식으로 그 위에 겹쳐 그리는 장식 뷰다.
- 낭독 팁(코드로 강제하지 않음, 렌더러 안내): 여러 자리 숫자를 화면 낭독기가 통째로
  큰 수("이십삼만사천오백육십칠")로 읽을 수 있다. 자릿수 낭독이 필요하면 렌더러가
  접근성 이름/값에 숫자 사이 공백을 넣어 한 자씩 읽히게 할 수 있다 — 이건 제품
  카피(어떻게 띄어 읽을지)의 문제라 composer 콜백을 새로 만들지 않고 문서로만
  안내한다.

## 공개한 축 / 배제한 축

| 축 | 상태 |
| --- | --- |
| `value`(controlled, 하나의 문자열) | 공개 |
| `availability`(enabled/disabled/readOnly/busy) | 공개 — 서버 인증 중 `busy` |
| `validation`(valid/invalid) | 공개 — 오류 카피는 Field의 `error` 슬롯 |
| 칸별 포커스·칸별 접근성 발화 | **배제**(의도적) — 위 판정 참고 |
| 영숫자 문자 집합 | **배제** — 측정된 요구 없음 |
