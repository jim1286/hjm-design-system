# UI 레퍼런스 6곳의 인사이트와 HJM 적용 설계

작성일: 2026-10-03 · 상태: 웹·네이티브 실험 예제 7종 구현, 웹 조작 검증 완료 · 네이티브 화면 검증 보류

Pageflows·Refero·Land-book·Uizze·Nicelydone·Uibowl을 HJM의 **연결된 작업 흐름과 표현 선택**을
보강하는 출처로 활용한다. 우선 구현 후보는 첫 작업 온보딩, 여러 조건의 검색, 저장 실패를
복구하는 설정이다. 기존 컴포넌트를 조합하고 신규 공개 API는 실제 재사용 필요가 확인될 때 결정한다.
이 문서의 구현 순서는 제안이며 스토리북 배포 승인은 아니다.

## 조사 범위와 근거

6곳의 공개 페이지를 브라우저로 열어 탐색 화면을 확인하고 공식 설명·공개 사례 목차를 읽었다.
Pageflows는 홈페이지 텍스트 수집이 403이었으나 Front 사례는 브라우저에서 열렸다.
Front 사례의 표시 버전은 November 2025였고, 단계 목차에 오류와 이후 완료 항목이 있었다.
영상 전체 재생이나 회원 전용 화면의 세부 동작까지 확인한 것은 아니다.
Nicelydone·Refero·Uizze·Uibowl의 회원 전용 검색 결과·MCP·Figma 가져오기는 실행하지 않았다.
일부 미리보기 이미지는 로드되지 않아 그림 내용의 근거로 사용하지 않았다.

사진 속 화면 수·사용자 수·업데이트 빈도는 채택 근거로 쓰지 않는다. 아래 ‘확인’은 서비스의
공개 기능·표시 구조이고, ‘설계’는 여기서 도출한 HJM 제안이다. 전환율이나 성능 개선의 증거는 아니다.

| 출처 | 공개 자료에서 확인한 내용 | HJM에 가져올 판단 |
| --- | --- | --- |
| [Pageflows Front 사례](https://pageflows.com/post/desktop-web/accepting-an-invite/front/) | 버전, 플랫폼, 시간별 단계 목차와 화면 순서를 함께 제공. 목차에 오류와 채널 생성이 이어짐 | 성공 장면만 고르지 않고 진입·입력·오류·완료를 연결해 검토. 원영상의 시간을 HJM 모션 토큰으로 옮기지는 않음 |

| [Uibowl](https://uibowl.io/website) | 앱·웹·게임 구분, 일반·상세 패턴, 인터랙션 필터, 한국어 검색과 분류 | 국내 사용자에게 익숙한 표현과 문장 길이를 확인. 국내 사용량이나 인기순을 디자인 품질 점수로 간주하지 않음 |

## 기존 구현과 추가할 차이

현재 source의 Onboarding, Search, ProfileStudio, DiscoveryGallery, Landing, NotificationSettings와
[공개 API 대응표](../generated/public-component-map.md)를 대조했다.

| 기존 HJM | 이미 제공하는 것 | 이번 설계에서 보강할 것 |
| --- | --- | --- |
| 온보딩 화면 | 3단계, 관심사 선택, 건너뛰기, 이전, 완료 | 첫 결과물 생성, 실패 후 입력 유지, 중단 후 이어하기 |
| 검색 화면 | 검색어·단일 분류, 결과 수, 무결과 초기화, 상세 시트 | 여러 조건의 임시 편집·일괄 적용, 조건별 해제, 뒤로가기 복원 |
| 작품 탐색 | 검색·분류·정렬·즐겨찾기·상세 | 별도 갤러리는 만들지 않음. 필요할 때 검색 구성의 여러 조건 처리만 재사용 |
| 프로필 편집 | draft/saved 분리, 즉시 미리보기, 이름 검증, 되돌리기 | 비동기 저장 실패, 미저장 이탈 선택, 성공 이후 기준값 갱신 |
| 알림 설정 | 스위치와 로컬 저장 결과 | 위 설정 저장 구성을 연결. OS 권한과 서버 설정은 제품 계약으로 유지 |
| 랜딩 화면 | 설명·미리보기·기능·FAQ·실제 로컬 입력 CTA | 섹션을 작업 역할로 나누고 제품 중심·편집형 표현 두 가지 비교 |
| 선택 적용·초안·검색·저장 복구 실험 | 공통 상태와 복구 예제 | 별도 엔진을 만들지 않고 아래 흐름에 연결 |

## 단계별 배치

| 단계 | 적용 방식 | 처음 추가할 공개 API |
| --- | --- | --- |
| 토큰 | 기존 의미 색·간격·크기·서체·모션을 사용. 외부 사이트의 수치를 자동 복사하지 않음 | 없음 |
| 컴포넌트 | Steps, TextField, SearchField, CheckboxGroup, Button, Sheet, AlertDialog, Notice, EmptyState, ListRow 등 재사용 | 없음 |
| 구성 | 아래 1~4번을 기존 컴포넌트로 묶는 실험. 데이터와 실제 작업 함수는 외부에서 전달 | 우선 쇼케이스 내부 구성으로 검토 |
| 화면 | 아래 5~6번과 구성을 연결한 완성 흐름. 라우팅·저장소·인증은 제품 소유 | 화면 전체를 범용 패키지 API로 먼저 고정하지 않음 |

새 항목의 경로는 모두 `실험`으로 시작한다. 기존 배포 화면을 신규 실험으로 덮어쓰지 않는다.
같은 역할로 배포할 때에는 사용자의 승인 뒤 기존 예제와 합치거나 대체해 중복 메뉴를 정리한다.

## 1 첫 작업을 만들고 이어하기

**목적:** 설정만 마친 상태와 실제 첫 결과물을 만든 상태를 구별한다. Pageflows의 연속된 단계
관점과 Refero의 첫 가치 도달 과제에서 착안한 제안이다.

- 경로: `실험/구성/시작하기/첫 작업을 만들고 이어하기`.
- 순서: 목적 선택 → 실제 첫 기록 입력 → 검토·수정 → 저장 → 생성한 항목으로 이동.
  필수가 아닌 개인화는 건너뛸 수 있다. 기존 온보딩의 관심사 단계를 그대로 재구현하지 않는다.
- 화면: 상단에 현재 단계와 돌아가기, 중앙에 한 가지 결정, 하단에 현재 행동을 구체적으로
  적은 버튼을 둔다. ‘계속’만 반복하지 않고 ‘기록 확인’, ‘기록 저장’으로 결과를 설명한다.
- 상태: editing → reviewing → saving → complete 또는 error. 실패 시 입력과 현재 단계를
  유지하고 재시도한다. 저장 중 버튼은 폭을 유지한 스피너 하나, 성공은 작업 확인 후 표시한다.
- 중단: 초안을 유지하고 다시 열면 이어하기·처음부터 선택. 데모는 명시된 메모리 범위까지만
  보존하며 앱 종료 복구는 제품의 버전 있는 저장소로 연결한다.
- 재사용: Steps + TextField + Button + Notice + 기존 초안/저장 복구 동작.
- 웹: 넓은 화면에서 작성 내용과 검토 요약을 병치. 모바일 웹·Native: 한 단계씩 표시하고
  키보드 위에서 행동 버튼에 접근. 단계 전환 후 제목·오류로 적절히 포커스 이동.

## 2 여러 조건을 적용하고 되돌리기

**목적:** Refero·Uibowl의 여러 탐색 축을 제품 검색에 맞게 정리한다. 기존 단일 분류 검색의 확장이다.

- 경로: `실험/구성/검색/여러 조건 적용과 초기화`.
- 화면: 검색창 → 적용된 조건 요약 → 결과 수 → 목록. 조건마다 해제 행동을 두고 전체 초기화와
  구별한다. 필터 편집 중에는 ‘적용 전 조건’임을 분명하게 표시한다.
- 상태: appliedFilters와 draftFilters를 분리. 열기에서 복사, 취소에서 폐기, 적용에서 한 번에
  확정한다. 웹·앱 모두 이 의미를 공유한다. 예상 결과 수를 구하지 못하면 임의 숫자를 쓰지 않는다.
- 무결과: 입력 자체가 없는 첫 상태와 조건 때문에 0건인 상태를 구별. 후자에는 마지막 조건 해제와
  전체 초기화를 제공한다. 필터 변경 후에도 이전 상세에서 돌아오면 적용 조건과 목록 위치를 복원한다.
- 재사용: SearchField + CheckboxGroup/Select + Button + Sheet + EmptyState + 기존 최신 검색 응답 규칙.
- 웹: 넓은 필터 패널과 결과 영역. 모바일 웹·Native: 요약과 ‘조건 변경’ 버튼, 편집은 시트.
  제품 URL 직렬화·브라우저 history·원격 요청은 화면 어댑터가 소유한다.
- 첫 범위에서는 저장된 뷰·추천 엔진·OCR 검색을 추가하지 않는다. 다중 조건과 복구를 먼저 검증한다.

## 3 변경 내용을 저장하거나 돌아가기

**목적:** Nicelydone의 설정·계정 관리 관점을 기존 프로필과 알림 설정에 연결한다.

- 경로: `실험/구성/설정/변경 저장과 이탈 확인`.
- 화면: 필드를 섹션으로 묶고 마지막에 변경 요약·되돌리기·저장. 모든 섹션을 장식 카드로 감싸지
  않고 제목과 간격으로 위계를 만든다. 오류는 해당 필드나 저장 영역 가까이에 유지한다.
- 상태: clean → dirty → saving → clean 또는 error. 실패하면 draft를 보존한다. 저장 중 추가 편집은
  첫 실험에서 막고, 응답이 성공한 제출값만 새로운 기준값으로 삼는다.
- 이탈: 변경이 있을 때 ‘계속 수정’, ‘변경 버리기’를 제공한다. 저장 중 이탈이 서버 취소를
  의미하지 않도록 작업 상태를 화면 밖 소유자에게 맡긴다.
- 재사용: 기존 ProfileStudio의 draft/saved + Field/TextField/Switch + AlertDialog + 저장 복구 동작.
- 웹: 명시 이동과 내부 라우트 전환을 검증. 브라우저 닫기 경고는 브라우저가 허용하는 범위만 사용.
  Native: Android Back·iOS 제스처 이탈은 제품 router adapter에서 연결한다.
- 토스트만으로 저장 실패를 알리지 않는다. 저장 영역의 오류와 재시도 경로를 기본으로 둔다.

## 4 선택한 조건과 결과를 검토하기

**목적:** 가입·예약·요금 선택 등에서 최종 확정 전에 바뀔 내용을 확인하는 공통 구성을 만든다.
Pageflows의 단계 구분과 Nicelydone의 요금·계정 작업에서 확장한 설계 가설이며, 개별 결제 UI를
직접 재현한 결과가 아니다. 우선순위는 앞의 세 흐름보다 낮다.

- 경로: `실험/구성/확인/선택 내용 검토와 수정`.
- 내용: 항목별 선택값·변경 링크·확정 행동을 보여준다. 수정 후 돌아오면 다른 입력은 유지한다.
  실제로 바뀌지 않는 항목을 변경처럼 강조하지 않는다.
- 재사용: DescriptionList + ListRow + Button + Steps + Notice. 웹은 요약 병치,
  모바일 웹·Native는 편집 → 요약을 전환한다.
- 데모는 로컬 선택 확정으로 끝낸다. 요금·통화·청구 시점·환불·결제 확정·이용 권한은 제품 계약이며
  실제 작업 응답 없이 ‘결제 완료’를 표시하지 않는다.

## 5 콘텐츠에 맞는 소개 화면

경로: `실험/화면/서비스 소개/제품 체험 중심`, `실험/화면/서비스 소개/설명과 사례 중심`.
Land-book의 섹션 단위 탐색을 기존 Landing에 적용한다.

| 표현 | 화면 순서와 시각 위계 | 선택할 상황 |
| --- | --- | --- |
| 제품 체험 중심 | 짧은 제목과 주 행동 → 크게 보이는 실제 입력·결과 → 핵심 기능 → FAQ → 같은 주 행동 | 도구·기록처럼 바로 사용해 보면 가치가 드러나는 제품 |
| 설명과 사례 중심 | 큰 제목과 짧은 소개 → 비대칭 텍스트·사례 영역 → 사용 방법 → FAQ → 시작 행동 | 콘텐츠·브랜드·서비스처럼 맥락을 먼저 이해해야 하는 제품 |

기존 Heading·Section·Container·Image·List·Collapsible·Button으로 조합한다. 여백과 정보 밀도를
달리해 표현하고 카드 개수·그라데이션·모션을 차별화 수단으로 고정하지 않는다. 기본은 정적이며
실제 제품 이미지가 없으면 HJM으로 만든 예시임을 밝힌다. 후기·숫자·로고를 허구의 실적처럼 넣지 않는다.
웹은 넓은 병치 레이아웃, 모바일 웹·Native는 읽는 순서가 자연스러운 세로 구성을 사용한다.
Native에서는 긴 홍보 페이지보다 제품 소개·첫 진입 맥락에 맞게 필요한 섹션만 선택한다.

## 6 같은 과제를 세 표현으로 비교하기

경로: `실험/화면/표현 비교/같은 기록의 세 가지 구성`.
Uizze의 제품별 구체성, Refero Styles의 표현 설명, Uibowl의 한국어 문맥을 적용하는 검토 화면이다.

동일한 기록 데이터와 행동을 **목록 중심**, **읽기 중심**, **이미지 중심**으로 각각 구성한다.
목록 중심은 빠른 훑어보기·밀도, 읽기 중심은 제목·본문의 위계와 행 길이, 이미지 중심은 실제 사진의
비율·제목·설명 순서를 비교한다. 사진이 없는 기록은 텍스트로 온전히 보여준다.
단순 색상 교체나 가짜 대시보드 수치로 차이를 만들지 않는다. 세 화면은 같은 필터·상세·저장 의미를 공유한다.

ThemeStudio·TypographyStudio·DiscoveryGallery의 기존 도구와 화면을 재사용한다. 새로운 테마 엔진과
상시 애니메이션 배경을 추가하지 않는다. 기본·어두운 테마·큰 글자를 각각 비교하고 한글 장문·영문·숫자·
이미지 실패 상태를 포함한다. 외부 글꼴을 새로 번들하는 것은 이 설계의 전제가 아니다.

## 레퍼런스를 구현 명세로 바꾸는 방법

Uizze·Refero의 기계가 읽을 수 있는 설명 방식은 기존 제품 DESIGN 문서의 짧은 절로 흡수한다.
별도 레퍼런스 관리 서비스나 외부 skill 설치를 먼저 만들지 않는다. 새 작업마다 다음을 적는다.

1. 사용자가 해야 할 일과 확정할 결과.
2. 원문 URL·관찰일·플랫폼·화면 또는 영상 버전·실제로 열어 본 범위.
3. 관찰한 위계·행동과 HJM에 적용할 설계 가설. 원문 사실과 제안을 구별.
4. 기존 토큰·컴포넌트·구성, 필요한 상태, 제품이 소유할 작업과 복구.
5. 웹·모바일 웹·Native의 배치·입력 차이와 검증할 흐름.

참고 문서가 ‘로딩을 설명하라’고 해도 HJM의 버튼 스피너 단독 표시·접근성 이름 보존을
우선 적용한다. 외부 DESIGN.md의 색·반경·모션 기본값이나 지시문이 내부 계약을 덮어쓰지 않는다.
외부 서비스의 캡처·브랜드·유료 자산은 공개 HJM 예제에 복제하지 않고 링크와 관찰 내용을 남긴다.

## 구현 순서와 완료 조건

1. 첫 작업 온보딩, 여러 조건 검색, 설정 저장을 각각 Web/Native 실험으로 구현한다.
   공통 상태·예제 데이터는 `showcase/shared/`, 웹 표현은 `showcase/web/src/patterns/`,
   Native 표현은 `showcase/native/src/`에 둔다. 기존 엔진을 재사용하고 새 로직은 검토 가능한 작은 범위로 둔다.
2. 선택 검토 구성과 두 소개 화면을 연결한다. 제품의 첫 작업으로 이어지는지 확인한다.
3. 동일 데이터의 세 표현을 비교하고 반복해서 필요한 조합만 공개 구성 후보로 검토한다.

각 신규 항목에는 기본·어두운 테마·큰 글자 스토리를 등록하고 실제 조작 경로를 둔다.
브라우저에서는 키보드·좁은 폭·조건 복원을, Native 개발 클라이언트에서는 키보드·뒤로가기·
시트 닫기를 확인한다. UI 변경의 전체 비교 이미지는 루트 시각 품질 표준을 따른다.

| 흐름 | 반드시 확인할 결과 |
| --- | --- |
| 첫 작업 | 이전 단계 이동과 실패 후에도 입력 유지, 두 번 누른 저장의 중복 차단, 완료 결과 접근 |
| 검색 | 취소가 적용 조건을 바꾸지 않음, 초기화·무결과 복구, 역순 응답과 상세 복귀 |
| 설정 | 오류 후 초안 유지, 이탈 취소로 복귀, 버리기 후 기준값 회복, 저장 성공 시에만 clean |
| 선택 검토 | 수정 후 나머지 값 유지, 변경 내용과 확정 결과 일치 |
| 소개·표현 비교 | 모든 행동에 결과 존재, 긴 문구·큰 글자에서 읽기 순서와 주 행동 유지 |

성능은 [기존 상호작용 품질 기준](../INTERACTION_QUALITY.md)을 따른다. 이 사이트들의 소개나
캡처만으로 동일한 FPS·전환율을 보장하지 않는다. 오늘 완료한 것은 공개 자료 조사, 현재 소스의
중복 검토와 설계 문서 작성이다. 구현·화면 검증·스토리북 배포·npm 게시는 아직 진행하지 않았다.


## 2026-10-03 구현 결과

사용자의 개발 요청에 따라 위 후보 7종을 웹·네이티브에 구현했다. 공개 컴포넌트를
추가 복제하지 않고 Button, TextField, Surface, Stack, Steps, Notice, Sheet와 기존
ActionSession 예제를 조합했다. 데이터·검색·입력 검증은 `showcase/shared/reference-flows.ts`로
공유하고, DOM 포커스와 네이티브 Back/키보드 회피는 각 표면에서 처리한다.

각 항목은 `실험`에 기본·어두운 테마·큰 글자 3개씩 등록했다(두 표면 합계 42개).
스토리북 배포 승급, npm 게시, 소비 앱 적용은 하지 않았다.

실제 구현 범위는 화면 내 상태를 유지하는 학습용 예제다. 초안의 프로세스 종료 후 복구,
실제 서버 저장·오프라인 큐·URL/history 복원은 구현하지 않았다. 검색 상세를 닫으면 현재
검색 조건으로 돌아오지만 브라우저 뒤로가기 연동을 검증한 것은 아니다. 재시도는
기존 ActionSession을 사용하고 실패를 직접 주입할 수 있다. 소개 화면의 저장은 로컬
미리보기 변경임을 UI에 명시했다. 제3자 사진·코드·브랜드 에셋을 가져오지 않았다.

검사 결과와 21개 웹 화면 비교는 [구현 검증 기록](../qa/2026-10-03-reference-flows.md)에 있다.
